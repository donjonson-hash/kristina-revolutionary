# Идемпотентность эмоциональных реакций

Задача: повторное входящее событие Telegram не должно ещё раз менять эмоции,
если процесс завершился после эмоционального commit, но до сохранения диалога.
Это защита одного перехода состояния, не обещание атомарного LLM-вызова или
доставки сообщения через внешний Telegram API.

## Контракт

Persona создаёт `EmotionalEvent` из рассчитанного router `session_id`,
transport `event_id` и точного текста входящего сообщения. Переданный извне
`context["emotion_event"]` не используется: stamp создаётся заново.

Сессия включает канал, чат и пользователя. В эмоциональную БД сохраняются
SHA-256 сессии, event ID, SHA-256 текста и время применения; исходный текст,
цитаты appraisal и открытый идентификатор сессии туда не копируются.
Хеш связывает данные, но сам по себе не удостоверяет личность отправителя.

Далее stamp передаётся через `BrainBridge → EmotionalAgent → MoodEngine →
EmotionalCore`. При сбое bridge запасной путь Persona использует тот же stamp,
поэтому fallback не может незаметно применить обычный user-message эффект второй раз.

## Запись и повтор

В существующую эмоциональную SQLite-базу добавляется таблица
`emotional_message_events` с уникальным ключом `(session_sha256, event_id)`.
Проверка receipt, применение реакции, запись receipt и эмоционального payload
проходят в одной транзакции `BEGIN IMMEDIATE`.

- Нет receipt: применяется первое событие, состояние и receipt фиксируются вместе.
- Есть receipt с тем же хешем текста: user/appraisal effects не повторяются.
- Есть receipt с другим текстом: событие отклоняется, состояние и диалог не перезаписываются.
- Ошибка записи: откатываются и реакция, и receipt; корректная повторная попытка разрешена.
- Другой чат, пользователь или канал с тем же message ID: независимое событие.

Конкурирующие экземпляры ядра используют SQLite-уникальность и транзакцию,
а не только локальный Python lock. При replay продолжает учитываться прошедшее
время: состояние не замораживается в момент первой реакции и не откатывает
эмоции, уже изменённые другими сообщениями.

Shadow observer уведомляется только о впервые применённом событии и только
после commit. Replay не создаёт второе shadow-наблюдение.

## Границы и совместимость

- Защищён основной Persona-путь Telegram со стабильным входящим event ID.
- Anonymous/legacy вызовы без session/event ID сохраняют прежнее поведение.
  Прямой внутренний вызов bridge/ядра должен явно передать stamp для этой гарантии.
- В неперсистентном `EmotionalCore` дедупликация действует только в жизни объекта.
- Состояние, traits, модель эмоций, расписание и experiment receipts не сбрасываются.
  Миграция только создаёт новую таблицу.
- Старые эмоциональные переходы не получают выдуманных receipts. Защита относится
  к событиям, впервые зафиксированным новой версией; завершённые старые диалоги
  по-прежнему защищены существующим dialogue receipt.
- После аварии appraisal и генерация ответа могут быть вызваны повторно. При
  ином appraisal повторная эмоциональная реакция всё равно не применяется:
  для этого event побеждает первый успешный эмоциональный commit.
- Две БД не превращаются в одну транзакцию. История, доставка и LLM-биллинг
  не получают общей exactly-once гарантии.
- В рамках этой правки receipts не удаляются по TTL: удаление позволило бы
  слишком позднему повтору снова изменить эмоции.

## Проверки

```bash
python -m pytest tests/test_emotional_event_idempotency.py -q
python -m pytest tests/ -q
```

Проверяются SQLite и in-memory режимы, свежий объект после рестарта, разные
сессии с одинаковым event ID, восемь конкурирующих writers, конфликт текста,
rollback обеих записей, миграция старой базы, сохранение experiment receipts,
течение времени, observer и fallback Persona.

Межпроцессный тест запускает настоящий путь `bot.handle_message → router →
Persona → BrainBridge`. Первый процесс принудительно завершается через
`os._exit(72)` в начале генерации ответа, когда эмоциональная транзакция уже
завершена, но диалог ещё не сохранён. Новый процесс получает то же Telegram-событие:
сохраняется один обмен, одна emotional receipt и одна реакция вместо двух.

Провайдеры и Telegram delivery в тестах заменены; реальные пользователи не
получают сообщений. Этот PR не меняет Scout, сверку документов, PR восстановления
runtime-контекста или production-конфигурацию.

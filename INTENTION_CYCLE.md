# Собственный замысел: первая проверяемая работа

Кристина может превратить сохранённый интерес из разговора в небольшую техническую гипотезу, отложить её проверку, получить реальные наблюдения и позже вернуться к ним. Результат меняет моделируемое эмоциональное состояние. Цикл поддерживает календарные пробы и исследование JSON Schema из публичного GitHub. Самостоятельное программирование и изменение внешних систем в него не входят.

## Что доступно

Базовый инструмент — `calendar_validation`: сравнение строгого формата `YYYY-MM-DD` с существованием календарной даты. Модель выбирает причину проверки, одну из двух гипотез и 1–8 синтетических примеров с предсказаниями. Обычный Python проверяет формат регулярным выражением и дату через `date.fromisoformat`. Строки остаются данными; код из ответа модели не исполняется. Runner не обращается к сети, файлам, shell или OpenClaw.

Например, `2024-02-30` соответствует формату, но не существует в календаре. Это контрпример к гипотезе «формат гарантирует календарную корректность». Другой вид гипотезы проверяет все предсказания модели о валидности примеров. Отсутствие контрпримеров означает согласие только с проверенной выборкой, а не доказательство универсального утверждения.

Для базового инструмента планировщик получает сохранённый интерес и его исходную цитату. При отсутствии подходящей технической темы он возвращает `skip`. Разговор о поездке и дата отъезда сами по себе не повод проверять календарную валидацию.

## Состояния и ритм

| Состояние | Значение |
| --- | --- |
| `planning` | Попытка планирования записана в SQLite; выбираются источники и гипотеза |
| `planned` | Строго проверенный план сохранён; выполнение возможно через 30 минут |
| `running` | План проверяется отдельным процессом; завершённого результата ещё нет |
| `completed` | Наблюдения фиксированного runner сохранены вместе со статусом |
| `declined` | Модель явно отказалась от неподходящего эксперимента |
| `failed` | Планирование прервалось/завершилось ошибкой либо сохранённый план невалиден |
| `cancelled` | Исходный интерес заменён или закрыт |

Отдельный JobQueue heartbeat каждую минуту проверяет возможность работы. Ночью по Стокгольму, при энергии ниже 0.45 или любопытстве ниже 0.65 новая работа и выполнение откладываются. Применение уже полученного результата и восстановление прерванного планирования не зависят от желания работать.

На всю Кристину допускается один активный замысел. Глобальный бюджет — одна попытка планирования за 6 часов; версия интереса вместе с версией GitHub-источника рассматривается максимум один раз. Бюджет сохраняется до обращения к модели. Базовый календарный план требует одного вызова (600 выходных токенов, 20 секунд), исследование репозитория — максимум двух (700 и 1000 токенов, по 20 секунд), без повторов. Вся подготовка репозитория ограничена 90 секундами. `planning` и `running` с истёкшей двухминутной арендой становятся `failed`; поздний ответ не восстанавливает их. Это ограничение стоимости, а не гарантия выбора эксперимента.

## Память, эмоции и доставка

`agent_intentions` и `agent_work_budget` создаются при инициализации существующей БД диалогов. Замысел связан с конкретными `session_id` и `source_message_id` из `cognitive_interests`; источник должен быть реальным сообщением пользователя этого разговора. Уникальный индекс запрещает два активных замысла, транзакции `BEGIN IMMEDIATE` защищают захват работы и сохранение результата.

Смена/закрытие интереса отменяет активный замысел в той же транзакции, что сохраняет диалог. Исторические результаты остаются в БД, но больше не подставляются в контекст нового интереса. `/clear` удаляет замыслы и результаты этого разговора вместе с его памятью. Глобальный бюджет остаётся, поэтому очистка не позволяет обойти лимит вызовов. Ожидание модели не удерживает блокировку разговора; при возврате ответ повторно проверяет существование исходной версии.

`inconclusive` сохраняется как завершённая проверка без достаточных оснований для вывода и не меняет эмоции. Для остальных исходов после `completed` worker передаёт исход в `EmotionalCore.record_experiment`:

- `supported_on_cases`: удовлетворение (`happiness`) +0.03;
- `counterexample_found`: любопытство +0.04 и раздражение +0.01.

Это небольшие заданные эвристики, а не вывод о настоящих переживаниях. Изменения нормализуются, обычное восстановление состояния со временем сохраняется. Никакого фиктивного события `user_message` не создаётся.

В БД эмоций таблица `experiment_effects` хранит только UUID результата, исход и время применения. Квитанция и эмоциональное состояние фиксируются одной транзакцией; отметка доставки затем записывается в БД диалогов. Сбой между этими записями приводит к безопасному повтору доставки без повторного изменения эмоции, в том числе после перезапуска. Формат payload остаётся v2. После `/clear` уже пережитое изменение общего состояния не откатывается; квитанции без текста диалога остаются для дедупликации.

Ответ Persona и существующая проактивная генерация получают замысел только из своей текущей беседы. Намерение маркируется отдельно от `tool_result`; утверждать выполненную проверку можно только по сохранённому `completed/result`. Это данные и инструкции для генерации, а не жёсткая гарантия отсутствия любых галлюцинаций в свободном тексте.

Выполнение не зависит от отправки Telegram-сообщения. Worker восстанавливает работу из БД даже при пустом `active_chat_ids` после перезапуска. Доставка использует прежний механизм инициативы: список активных Telegram-чатов пока хранится в памяти и вновь наполняется при обращении пользователя. Поэтому завершённый результат после перезапуска может ждать следующего разговора; отдельной гарантированной рассылки результатов нет.

## Проверка и эксплуатация

Автоматические тесты проходят без внешних LLM/Telegram-вызовов: проверяются реальные календарные наблюдения, перезапуск между этапами, конкурентный захват, отмена во время планирования, границы стоимости, транзакционный откат, повтор применения эмоции и изоляция контекста. Запуск: `python -m pytest tests/ -q`.

Для ручной проверки после деплоя обсудить с Кристиной техническую проблему календарной валидации. Если appraisal сохранит соответствующий интерес, а состояние допускает работу, очередной heartbeat предложит планировщику выбрать эксперимент. Проверять этапы в `agent_intentions` и квитанции в `experiment_effects`; отсутствие плана может означать осознанный `skip`, паузу состояния или занятый бюджет. Через минимум 30 минут после сохранения плана можно спросить о результате. Удаление беседы во время ожидания должно предотвратить её восстановление.

Миграция с PR21 атомарно переносит существующие намерения в таблицу с версией GitHub-источника, `evidence` и состоянием `running`; сохраняет планы, результаты и отметки доставки. Существующие календарные планы не превращаются в проверки репозитория. Действующий pre-deploy backup сохраняет обе SQLite-базы перед рестартом. Для полного отката к PR21 следует остановить сервис, вернуть код и восстановить обе базы из согласованной резервной копии: предыдущий worker не поддерживает новые планы.


## Исследование репозитория

Пользователь присылает обычную HTTPS-ссылку `github.com/owner/repo`, `/tree/ref/folder` или `/blob/ref/file` и обсуждает гипотезу. Источник берётся только из сообщений пользователя той же беседы, включая историю за пределами контекста LLM (просматриваются последние 100 сообщений с GitHub-ссылками). Повтор одной и той же ссылки сохраняет текущую работу; другая ссылка создаёт новую версию. Изменившийся источник скрывает устаревший результат и отменяет активную работу при ближайшем тике либо перед фиксацией результата. `/clear` удаляет также источник, поскольку он хранится в истории беседы.

`repository_research.py` фиксирует commit SHA через GitHub API, получает дерево и читает содержимое по Git blob SHA с проверкой хеша. Публичные репозитории поддерживаются без ключа в пределах GitHub API rate limit; необязательный `GITHUB_READONLY_TOKEN` повышает доступный лимит. Права на запись не требуются. HTTP redirects и private repositories отвергаются. В ссылках поддерживается ref из одного URL-сегмента; для веток со слешем используйте commit SHA.

Модель выбирает до четырёх файлов из списка максимум 120 ранжированных путей, затем конкретное поле `date`/`date-time` и 1–8 синтетических примеров. Поиск идёт по именам путей, а не по непрочитанному содержимому. Ограничения чтения: 6 MiB на API-ответ, 5000 допустимых файлов в дереве, 300 KiB на файл, 800 KiB суммарно. Зависимости, symlink, бинарные и пути с признаками секретов исключаются. Неполное дерево не используется для эксперимента. Для схемы действует дополнительный предел 300000 байт. Прочитанные файлы могут содержать недоверенные инструкции; они передаются модели только как данные.

План хранит полную схему, путь, commit, Git blob SHA, SHA-256 и JSON Pointer. В `evidence` остаются метаданные и фрагменты выбранных файлов (до 5000 символов каждого с явной отметкой усечения). Эти фрагменты служат контекстом; утверждать полный аудит нельзя. В обычный диалог передаются фрагменты, план без полного текста схемы и завершённый результат.

`json_schema_format` запускает наш фиксированный worker, а не код репозитория. Он применяет jsonschema 4.26.0 к выбранному полю без FormatChecker, с ним и сравнивает результаты с независимым календарным парсером. Внутренние JSON Pointer `$ref` поддерживаются, внешние/файловые ссылки и вложенные идентификаторы схем отклоняются. Схема проверяется по своему диалекту. Нужны корректный контрольный пример и некорректный; недостаточная выборка даёт `inconclusive`. Секунды `:60` и год `0000` не поддерживаются и отклоняются до запуска.

Worker выполняется в отдельном процессе без унаследованных API-ключей, с лимитами 5 секунд wall time, 2 секунды CPU, 384 MiB памяти и 32 KB результата. Превышение, ошибка или отмена приводят к завершению процесса и отсутствию успешного результата. Родитель проверяет структуру результата и соответствие исходному плану. SQLite-транзакция и блокировка диалога во время процесса не удерживаются; перед сохранением повторно проверяются версия источника и наличие беседы.

Команда Telegram `/research` показывает сохранённый статус и фактические наблюдения со ссылкой на коммит. Она не вызывает LLM, не ускоряет работу и не отправляет сообщения другим пользователям. Проактивное возвращение к результату продолжает зависеть от прежнего механизма инициативы.

### Контроль на Drydock

13.09.2026 новый reader и worker реально прочитали SARIF-схему из `aiagent2046-coder/shipit` на commit `cd5fd2234936dcf5e8609510612364e6eca6a45e`, путь `tests/fixtures/sarif-schema-2.1.0.json`, SHA-256 `7c9688f0a1c4a4e1649ecc78521087e664729c1dff56ee8212ff195c7b16132a`. Проверено поле `/definitions/invocation/properties/startTimeUtc`.

| Синтетический пример | Без FormatChecker | С FormatChecker | Календарный парсер |
| --- | --- | --- | --- |
| `2024-02-29T12:00:00Z` | true | true | true |
| `2026-02-30T12:00:00Z` | true | false | false |
| `2026-13-12T12:00:00Z` | true | false | false |
| `2026-09-13T12:00:00Z` | true | true | true |

Получены два контрпримера на четырёх специально выбранных пробах. Это результат запуска нового инструмента разработчиком; не утверждение о самостоятельном выборе Кристины в продакшене, не статистика реальных отчётов и не доказательство ошибки работающего Drydock. Проверялось выделенное поле реальной схемы, а не полный SARIF-документ.

Сейчас в этот цикл не входят исполнение кода/тестов проекта, установка его зависимостей, ZIP-вложения, запись в GitHub, PR и деплой. Эти возможности нельзя обещать собеседнику как уже доступные.

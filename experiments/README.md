# Связи между эмоциональными состояниями: пилот Drydock → Kristina

Это **shadow-эксперимент**: детерминированные обработчики передают числовые импульсы
между существующими осями `EmotionalCore`. Синтетический offline replay остаётся
отдельным режимом. Теперь есть также выключенный по умолчанию observer проверенной
оценки из рабочего pipeline; его результаты не меняют ядро, память или ответы.

## Что перенесено из Drydock

Самостоятельно реализованы архитектурные принципы, проверенные в
[shipit на 405cc1f6](https://github.com/aiagent2046-coder/shipit/tree/405cc1f6dc47cecc2c2671ced9aad10ede644500):

| Механизм Drydock | Реализация пилота |
| --- | --- |
| Ограниченная очередь `app/scan/agent_chain.py` | Очередь активных связей; максимум 16 обработчиков на событие, по одной попытке |
| Проверка предложений до принятия | Передача по зарегистрированному ребру, отдельный verifier, затем атомарное обновление shadow-состояния |
| Копии при передаче данных | Изменение возвращённого результата или входных словарей не меняет принятое состояние |
| Привязка результата к исходным данным | Хеши события, правил и предыдущего принятого результата; происхождение `synthetic_fixture` |
| Контролируемая мутация и обратное восстановление | Отключение одного ребра, проверка именно утраты торможения, восстановление из изменённого графа |

Исходный код Drydock распространяется под AGPL-3.0-or-later. Код его сканера не
копируется и не импортируется; здесь новая небольшая реализация этих принципов.
Это не перенос SQL/AST-сканера и не запуск нескольких LLM-агентов.

## Модель

Сохраняются семь осей ядра: `energy`, `happiness`, `curiosity`, `anxiety`,
`loneliness`, `creativity`, `irritation`, каждая в диапазоне `[0.1, 1.0]`.
В первом опыте активны четыре связи:

| Источник | Получатель | Вес |
| --- | --- | ---: |
| anxiety | curiosity | −0.40 |
| curiosity | creativity | +0.50 |
| irritation | happiness | −0.30 |
| happiness | anxiety | −0.25 |

Веса — ручные параметры гипотезы, а не результат обучения или установленная модель
психики. Отрицательный вес тормозит получатель при положительном импульсе источника;
при отрицательном импульсе знак воздействия меняется. Слова «центры» и «связи» здесь
обозначают числовые состояния и обработчики событий, не биологические нейроны.

Для каждого события:

```text
direct_delta = state_after_event - state_before_event
offset = clip(exp(-elapsed_seconds / 7200) * previous_offset + W * direct_delta,
              -0.12, +0.12)
shadow_state = clip(baseline_state + offset, 0.1, 1.0)
```

Оба снимка события берутся в один момент, **после** обычного circadian evolution.
Суточное изменение состояния не считается новым импульсом. Базовое ядро продолжает
своё существующее затухание с τ=4 часа; добавка связей затухает отдельно с τ=2 часа.
В таблице результатов указаны безразмерные изменения состояния, не проценты эмоций.

Каждое активное ребро получает только прямой импульс. Эффект одного ребра не
возвращается в очередь и не становится источником для другого ребра в том же или
следующем событии. Поэтому даже циклический каталог не вызывает самовозбуждения.
Shadow-добавка не записывается в baseline; это намеренное ограничение первого опыта.

## Запуск и результаты

Из корня репозитория, Python 3.11+; внешние зависимости не нужны:

```bash
python -B -S -m experiments.replay_emotional_links --summary
python -B -S -m experiments.replay_emotional_links
```

Первая команда печатает компактный результат, вторая — полную трассу каждого
события: входные снимки, дельты, вклад каждого ребра, затухание, оба ограничения,
состояние и хеши. Команды не сохраняют файлы. Код возврата 0 означает прохождение
всех объявленных проверок; иначе 1. [result.json](result.json) — сохранённый компактный
результат этого запуска. Хеши служат проверке воспроизводимости внутри одной среды;
между платформами/версиями libm возможны последние разряды float.

Четыре одинаковые последовательности синтетических числовых событий проходят через
отдельные `EmotionalCore(db_path=None, clock=...)`:

1. **control** — существующее ядро, связи отсутствуют;
2. **linked** — все четыре связи;
3. **mutant** — только вес `anxiety → curiosity` заменён на 0;
4. **restored** — в mutant-копии этому ребру возвращён исходный вес.

| Воздействие | Измеренный новый вклад |
| --- | ---: |
| curiosity +0.08 | creativity +0.0400 |
| anxiety +0.06 | curiosity −0.0240 |
| irritation +0.06 | happiness −0.0180 |
| happiness +0.03 | anxiety −0.0075 |

У mutant исчезает только выбранное торможение; остальные связи сохраняют свои
результаты. Восстановленный граф, все состояния и полные трассы совпадают с linked.
Через четыре часа без событий остаётся `exp(-2) ≈ 13.53%` последней добавки.
Все 10 причинных/числовых проверок пройдены (`supported_on_cases`). Это подтверждение
механизма на данных fixtures, не доказательство улучшения диалога или субъективных чувств.

## Границы и проверки

- Публичный `LinkReplay.observe` по-прежнему принимает только `synthetic_fixture`.
  Рабочие события принимает отдельный адаптер, описанный ниже. Смысл текста эти
  слои не извлекают; оценка сообщения `assess_event` по-прежнему использует LLM.
- `source_ref` и хеши связывают числа с fixture, не доказывают подлинность внешнего
  события. Полные receipts не являются исполняемыми инструкциями.
- Максимум 128 принятых событий на replay. Старые ID не вытесняются: точный повтор
  возвращает исходный результат, повтор с другими данными отвергается. Эта гарантия
  действует только внутри одного объекта в памяти, не между перезапусками.
- Неверные входы, обратное время и сбой обработчика отклоняют событие без частичного
  обновления. Превышение бюджета действий возвращает `blocked`, сохраняя прежнее
  состояние. Отклонённый ID не считается принятым.
- При ограничении добавки и итогового состояния trace показывает потерянную величину.
  Чтение `sample` не меняет состояние и не порождает новых импульсов.
- Эксперимент не создаёт singleton ядра, BrainBridge, MoodEngine или event bus.
  Тест свежего процесса блокирует сеть, subprocess, SQLite и запись файлов и
  проверяет, что модули LLM/рабочего pipeline не загружены.

```bash
python -m pytest tests/test_emotional_links.py -q
```

## Observer проверенной оценки: включение и границы

Для контролируемого запуска можно передать observer явно:

```python
from emotional_core import EmotionalCore
from experiments.appraisal_observer import AppraisalLinkObserver
from brain_integration import BrainBridge

observer = AppraisalLinkObserver()
core = EmotionalCore(db_path="experiment-emotions.db", appraisal_observer=observer)
bridge = BrainBridge(emotional=core, memory=existing_memory)
# Обычный process_signal с appraise_event=True, session_id и event_id.
# После успешных событий: observer.receipts (отделённые копии).
```

Для обычного singleton `get_emotional_core()` единственный флаг —
`KRISTINA_EMOTIONAL_LINKS_OBSERVER=1`, заданный **до его создания**. По умолчанию флаг
отсутствует, observer не создаётся. Здесь он не включён в конфигурации и не развёрнут.
Чтобы выключить его в уже запущенном контролируемом опыте, присвоить
`core.appraisal_observer = None`; для штатного процесса убрать флаг и перезапустить.
Трассы находятся только в `core.appraisal_observer.receipts`; нет нового API,
автоматического экспорта, записи на диск или передачи результатов в промпт.

Путь события: Persona передаёт ID в `BrainBridge`, существующий Cortex делает одну
оценку, bridge проверяет её относительно текущего сообщения и состояния диалога,
затем тот же объект `Appraisal` идёт через `EmotionalAgent` и `MoodEngine` в ядро.
Observer не вызывает модель, `react`, `evolve` или дополнительную оценку.

Ядро берёт оба снимка внутри своего `RLock`; с SQLite оно сначала получает
`BEGIN IMMEDIATE` и перечитывает актуальное состояние. `before` находится **после**
суточной эволюции, `after` — после обычных изменений сообщения, оценки и ограничения
осей. У снимков один момент времени. Поэтому direct delta включает и существующие
эффекты `user_message`, и эффекты appraisal, включая насыщение диапазона, но не
изменения от прошедшего времени. Только после успешного commit ядро передаёт копии
observer. Отказ записи откатывает состояние и не оставляет shadow-receipt; ошибка
observer или его метаданных не отменяет обычное успешно завершённое событие.

`AppraisalLinkObserver` использует ту же очередь, числовую модель и verifier, что
синтетический replay; manifest маркирует режим `validated_appraisal_shadow_one_hop`.
Источник receipt — `validated_appraisal`. В provenance входят хеш сессии,
`brain_bridge.user_message`, ID события, хеш сообщения и полной проверенной оценки,
reaction и intensity. Сам текст сообщения, цитата и reflection не сохраняются.
Хеширование не является анонимизацией или доказательством достоверности сообщения.
Ошибки журналируются только по классу исключения.

- Shadow-состояния и цепочки receipts разделены по `(session_sha256, source_id)`.
  Существующее базовое ядро остаётся общим; это **не** переход к отдельным эмоциям
  для каждого пользователя. Observer следует прикреплять к одному экземпляру ядра.
- Требуется непустой session ID длиной не более 4096; анонимные события пропускаются.
  ID события допускает 1–80 ASCII-букв, цифр или `._:-`. При наличии используется
  ID транспортного события; без него bridge создаёт UUID для данного вызова.
  Такой UUID не распознаёт повторную доставку в другом вызове.
- Не более 16 потоков и 128 принятых событий **суммарно** на observer. Вытеснения нет.
  Точный повтор snapshot возвращает прежний receipt; тот же ID с другими снимками,
  временем или provenance отклоняется внутри своей сессии и источника.
  Observer не подавляет повторное применение обычного эмоционального события:
  транспортная дедупликация остаётся задачей router/памяти.
- При исчерпании бюджета, обратном времени, неверных данных или сбое обработчика
  shadow-состояние не меняется. Рабочее событие продолжается без trace. Пропуски
  не восполняются; трассу нельзя считать полной историей. Перезапуск обнуляет
  observer, offsets и ledger; durable exactly-once здесь не обещается.
- Receipt свидетельствует о commit **эмоционального события**, не о доставке ответа
  или commit всей переписки. Ошибка последующей генерации ответа не отменяет уже
  завершённое эмоциональное событие. Межпроцессная очередь receipts не реализована.
- Offset остаётся только shadow-числом: его не пишут в production state, базу,
  промпты, темп ответа или веса. Самоописания модели не становятся новыми фактами.
  Обучение, влияние связей на поведение и утверждения о субъективных чувствах
  не входят в этот этап; оценка полезности потребует отдельного опыта.

```bash
python -m pytest tests/test_appraisal_observer.py tests/test_emotional_links.py -q
```

Тесты проходят настоящий router → Cortex → validated appraisal → EmotionalCore →
Persona с подменой только транспорта модели и ожидания ответа. Проверяются один
appraisal-вызов, равенство baseline с выключенным observer, суточная граница снимка,
перечитывание SQLite, сериализация потоков, rollback, изоляция ошибок, бюджеты и ID.

# Модель эпизода, вопросов и инициативы

Диалог сохраняет не только текст, но и состояние совместного эпизода. Модель нужна,
чтобы Кристина учитывала пояснение в текущем ответе, давала место паузе и не задавала
один вопрос снова после смены вступительной фразы.

## Работающий путь

`AgentRouter → Appraisal → preview → Persona → save_exchange`.

Смысл нового сообщения извлекает существующий вызов `assess_event`. Он может вернуть
дополнительное поле `dialogue`. Новый отдельный вызов модели не добавляется. Оценка
состояния, проверка источника, переходы и решение о возможности инициативы работают
в Python без LLM. Старые оценки из шести полей продолжают приниматься.

`BrainBridge` проверяет предлагаемую оценку и ссылку на вопрос до эмоциональной
реакции. Чистый `preview_user` передаёт результат в prompt текущего ответа:
«объяснение получено» становится доступно сразу. Модель эмоций получает обычное
событие пользователя один раз в этом пути; второе событие из preview не создаётся.

Затем `PersistentMemory.save_exchange` одной SQLite-транзакцией сохраняет:

- пользовательское сообщение и ответ с именем агента;
- состояние эпизода и источники объяснений;
- журнал входящего события;
- существующий интерес и связанные изменения намерений.

Состояние разделено по ключу `[канал, чат, пользователь]`. Анонимные запросы не
могут подставить сохранённое состояние. Очистка беседы удаляет её новый журнал и
состояние вместе с прежней памятью.

## События и источники

При наличии `dialogue` принимаются ровно эти поля:

```json
{
  "scene_action": "keep",
  "scene_label": "",
  "scene_quote": "",
  "contact_action": "keep",
  "contact_quote": "",
  "answer_to": null,
  "answer_quote": ""
}
```

| Поле | Допустимые значения и смысл |
| --- | --- |
| `scene_action` | `keep`, `imagine`, `end` |
| `scene_label` | Название до 120 символов, только при `imagine` |
| `scene_quote` | Точная цитата текущего сообщения до 240 символов, для изменения сцены |
| `contact_action` | `keep`, `pause`, `resume` |
| `contact_quote` | Точная цитата текущего сообщения, для изменения разрешённой паузы |
| `answer_to` | ID существующего открытого вопроса этой беседы: `q:<message_id>` |
| `answer_quote` | Точная цитата ответа или явного отказа отвечать |

Непустые цитаты обязательны для действий; у неиспользуемых полей строки пусты.
Собственные реплики Кристины и старые пользовательские сообщения не могут быть
источником новой интерпретации. Ссылка на вопрос другой беседы отклоняется.
Проверка цитаты подтверждает происхождение слов, но не правильность их смыслового
толкования. Это ограничение семантического шага LLM сохраняется.

Общая сцена записывается как `shared_imagined`, с меткой `interpretation`, цитатой
и ID пользовательского сообщения. Она позволяет сохранять шутки и детали кафе.
Ни это состояние, ни свободный рассказ ассистента не получают статус проверенной
физической встречи. Метку не требуется повторять пользователю в каждой реплике.

Причина отсутствия сообщений остаётся `unknown`. Чтение истории, heartbeat и
проверка статуса не создают новых событий эпизода или повторных эмоциональных
эффектов. Суточное затухание эмоций продолжает работать как прежде.

## Вопросы и паузы

Вопрос регистрируется по сохранённой реплике ассистента и получает ID её строки в
памяти. В этой версии синтаксический детектор учитывает до восьми фрагментов с `?`
в первых 12 000 символах; он не является полным распознавателем намерения спросить.
Открытый вопрос хранится отдельно, последние восемь закрытых — со статусом
`answered` или `superseded`. Связанный ответ содержит свою цитату и ID пользователя.

`pause` действует восемь часов или до следующего сообщения пользователя — что
наступит раньше. Это конечная разговорная пауза, не постоянная отписка от контакта.
Внутренние желания Кристины могут продолжать меняться во время этой паузы.

Если после вопроса пользователь ещё не возвращался, инициатива приостанавливается.
Если он вернулся с другой темой, это не считается ответом на прежний вопрос и не
запрещает всю дальнейшую инициативу. Старый вопрос остаётся в памяти; повторять его
автоматически нельзя.

## Отправка инициативы

В действующем `bot.autonomous_proactive_tick` проверка происходит **до генерации**:

1. Нет активной паузы или неподтверждённой отправки.
2. Нет вопроса, после которого пользователь ещё не возвращался.
3. После последнего входящего сообщения ещё не отправлялась другая инициатива.
4. Прошло минимум два часа после последней сохранённой инициативы.
5. Существующий `DecisionEngine` тоже выбирает действие `message`.

Одна инициатива между пользовательскими сообщениями сохраняется в SQLite и
переживает перезапуск. Порог желания, пауза энергии и случайные возможности
инициативы остаются в прежнем планировщике.

В готовом тексте проверяются вопросы **во всём сообщении**, включая конец. Точное,
вложенное или достаточно похожее повторение сохранённого вопроса отклоняется без
нового LLM-вызова ради обхода запрета. Сравнение лексическое, не универсальная
семантическая проверка всех возможных перефразировок. Обычный ответ пользователю
получает закрытые вопросы в prompt, но его произвольная формулировка не доказывается
Python-валидатором.

Перед генерацией процесс занимает долговременную заявку `reserved`. Новое входящее
сообщение отменяет такие заявки ещё до ожидания блокировки беседы. Отправка возможна
только после повторной проверки `mark_sending`. Поэтому устаревшая заготовка не
отправляется после уже замеченного возвращения пользователя.

После подтверждённой отправки текст, вопрос и расход инициативы записываются
атомарно. Если соединение оборвалось после начала отправки, доставка неизвестна:
текст не записывается как доставленный и автоматическая повторная отправка
блокируется до нового пользовательского хода. Внешняя отправка и SQLite не могут
образовывать одну транзакцию. Запоздалое подтверждение старого хода сохраняет
фактически доставленный текст, но не открывает уже закрытый вопрос заново.

## Повторная доставка входящего сообщения

Telegram передаёт `event_id=telegram:<message_id>`; ключ беседы остаётся прежним.
Уже завершённый повтор возвращает сохранённый текст и имя агента без новой оценки,
генерации и эмоционального события. Тот же ID с другим текстом отклоняется.
Повтор одинакового текста с новым ID остаётся новым пользовательским событием.

Другие клиенты могут передать стабильный `event_id` в контекст Router. Без него
каждый вызов считается новым событием. Два одновременных Router возвращают первый
зафиксированный результат, даже если оба успели начать генерацию.

Эмоциональное ядро и диалоговая память остаются в разных БД. Гарантия повторного
использования завершённого события не означает атомарности эмоций и памяти при
сбое записи или одновременной обработке в нескольких процессах.

## Проверка и установка

```bash
python -m pytest tests/test_dialogue_model.py -q
python -m pytest tests/ -q
```

Новые поведенческие тесты проходят настоящий путь Router → BrainBridge → Persona
→ SQLite; внешние модели и Telegram заменены контролируемыми ответами. Они
воспроизводят общую сцену, пояснение заботы, тишину, перезапуск, новый сюжет вместо
ответа, повторную доставку и гонки. Это проверки исполнения модели; качество
извлечения смысла реальным провайдером требует отдельного наблюдения после установки.

Таблицы добавляются обычной инициализацией `PersistentMemory`; существующая история
сохраняется. Прошлые сообщения автоматически не превращаются в новые подтверждённые
события. Изменение подготовлено для ревью, сервер этой веткой не обновлялся.
Эксперимент весов эмоциональных связей из PR #25 остаётся отдельным: здесь
реализовано состояние диалога и его влияние на решение об инициативе.

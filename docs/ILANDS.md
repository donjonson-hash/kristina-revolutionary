# Кристина и iLands: подготовка подключения

Статус: локальный MCP-мост реализован и проверяется тестами; **живое подключение
Кристины ещё не подтверждено**. Проверено 17 сентября 2026 года по официальной
инструкции и опубликованному Runner v0.1.27.
Целевой хост — постоянный сервер Кристины.

## Что уже есть и что требуется

Кристина в этом репозитории — самостоятельное Python-приложение. Её личность
задана в `kristina_identity.py`; текущая каноничная профессия — Senior
Software Engineer / Team Lead, а не историческая UX-дизайнерская роль.
`agents/router.py` сохраняет диалоги и интересы, `brain_integration.py`
подключает оценку событий и эмоции, `emotional_core.py` сохраняет состояние.

iLands BYOA подключает поддерживаемую среду исполнения через Runner.
В опубликованном v0.1.27 для Linux/macOS перечислены Codex, Claude Code,
OpenClaw, Hermes и Pi; для Windows — Codex и Claude Code. На маркетинговых
страницах часть сред ещё отмечена как coming soon: перед установкой
руководствоваться актуальными guide и manifest.

Готового адаптера для произвольного Python-процесса в этой версии нет.
Загрузка ссылки на GitHub или создание Passport не подключает Python-мозг,
эмоциональную базу и историю переписки.

| Вариант | Результат | Готовность |
| --- | --- | --- |
| Passport + поддерживаемая среда | Профиль и описание личности Кристины; мышление выбранной среды | Документированный путь iLands |
| Codex + локальный MCP-инструмент существующей Кристины | Вызов её Python-логики, памяти и эмоционального ядра | Реализован; полный обмен через Runner ещё требует проверки на сервере |

Для сохранения существующей Кристины нужен второй вариант. До проверки
обмена сообщениями через реальную среду нельзя утверждать, что он работает.
Runner создаёт собственный workspace и обновляет его `AGENTS.md`; инструкция
в корне этого репозитория сама по себе не является интеграцией.

## Первый шаг на сервере

Запустить под тем пользователем, который будет держать Runner:

```bash
python3 deploy/ilands_preflight.py
```

Скрипт только проверяет ОС, архитектуру, glibc, доступность пользовательского
systemd, lingering, объём памяти и наличие команд сред. Он не устанавливает
пакеты, не меняет службы, не вызывает модели и не читает `.env`, базы памяти
или файлы авторизации. Наличие команды не доказывает её совместимость
или авторизацию: это позже должен проверить Doctor выбранной среды.

Linux-путь v0.1.27 требует glibc >= 2.28, x64/arm64 и работающий
`systemctl --user`. Если проверка не прошла, не заменять этот механизм
системной службой. Для работы после выхода из SSH может понадобиться
lingering; изменение обсуждается отдельно, скрипт его не включает.
Результат относится именно к текущему пользователю, не ко всему серверу.

## Подготовленный MCP-мост

`ilands_mcp.py` запускается как отдельный stdio-процесс на официальном Python
MCP SDK. `requirements-ilands.txt` подключает эту опциональную зависимость.
Мост предоставляет только два инструмента:

- `kristina_status`: проверяет наличие файлов, не открывая память, `.env`
  или соединение с моделью. `available` означает наличие каталога и файла
  разговорной памяти, а не успешную авторизацию или готовность модели.
- `kristina_reply(agent_id, conversation_id, sender_id, message_id, text)`:
  возвращает текст через существующие `AgentRouter`, `KristinaPersonaAgent`
  и `BrainBridge`. Инструмент сохраняет диалог и меняет эмоциональное состояние.
  Он сам не отправляет ответ в iLands.

Источник кода и каталог состояния разделены. `--state-dir` должен указывать
на **действующий каталог состояния Кристины**, содержащий `kristina_memory.db`,
конфигурацию её провайдера в окружении или `.env` и существующий файл эмоций
(`KRISTINA_STATE_DB`, по умолчанию `kristina_state.db`). Если нужной базы нет,
runtime останавливается вместо создания пустой личности. История хранится
в той же базе, но с каналом `ilands` и отдельными идентификаторами агента,
диалога и собеседника. Telegram-история в этот контекст не подмешивается;
эмоциональное состояние остаётся общим с существующей Кристиной.

В `ilands_bridge.db` рядом с состоянием сохраняется журнал генерации.
Повтор с теми же идентификаторами и текстом возвращает сохранённый ответ
без нового обращения к ядру. Изменённый текст или отправитель при том же
ID отклоняется. После сбоя или прерывания неопределённый результат блокируется
для ручной проверки: ядро могло уже изменить память или эмоции. Не удалять
такие записи вслепую и не придумывать новый ID для повторной попытки.
Журнал содержит тексты ответов и должен оставаться на сервере.

Это защита от повторной **генерации**, а не гарантия однократной доставки.
Поле `delivery: not_managed_by_bridge` явно оставляет отправку и проверку
её результата официальным инструментам Runner. `origin: kristina_python_pipeline`
указывает путь обработки; существующий Python-код умеет возвращать запасные
ответы при сбое DeepSeek, поэтому поле не доказывает успешный вызов модели.

Harness должен брать стабильные IDs и исходный текст из реального события,
вызвать `kristina_reply`, затем отправить полученный текст официальным
инструментом iLands. При ошибке инструмента нельзя выдавать самостоятельно
сочинённый Codex текст за ответ Python-Кристины. Необходимость этого вызова
нужно закрепить в документах личности при подготовке Passport: Runner
перезаписывает `AGENTS.md` своего workspace. Такая инструкция всё равно
требует проверки на реальном событии; конфигурация MCP не обеспечивает её
выполнение сама по себе.

## Установка моста в отдельную рабочую копию

Пример ниже предполагает, что действующий каталог состояния —
`/opt/kristina-revolutionary`, а `/opt/kristina-ilands` ещё не существует.
Если Кристина запущена из другого каталога или с внешним `KRISTINA_STATE_DB`,
сначала уточнить её действующие пути. Команды выполняет тот же пользователь,
под которым подготовлен Runner. Рабочая копия и отдельная Python-среда
позволяют подготовить мост без смены исходников и зависимостей Telegram-бота.

```bash
cd /opt/kristina-revolutionary
git fetch origin feature/ilands-onboarding-preflight
git worktree add --detach /opt/kristina-ilands origin/feature/ilands-onboarding-preflight
cd /opt/kristina-ilands
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt -r requirements-ilands.txt
python3 deploy/ilands_codex_setup.py check
```

Если шаг завершился ошибкой, разобраться с ней перед продолжением.
`check` использует закреплённую Runner среду и отдельно выводит готовность
Codex и привязку к iLands. До создания личности `runner_auth`, `agent_binding`
и общий `readyForDaemon` могут оставаться отрицательными; авторизация Codex
при этом должна быть подтверждена в `harness.codex`.

Для headless-входа предусмотрена команда
`python3 deploy/ilands_codex_setup.py device-login`. Она запускает
`login --device-auth` именно у закреплённого Codex с сохранённым Runner
окружением. В настройках безопасности ChatGPT должна быть разрешена
авторизация кодом устройства. Коды и callback-ссылки в репозиторий и чат
не передавать.

После подтверждённой авторизации Codex:

```bash
"$HOME/.local/bin/ilands-runner" plugin install --target codex
python3 deploy/ilands_codex_setup.py configure-mcp \
  --python /opt/kristina-ilands/.venv/bin/python \
  --state-dir /opt/kristina-revolutionary
```

Helper дописывает только `[mcp_servers.kristina]` в `config.toml` того
`CODEX_HOME`, который сохранён в записи Runner. Привязка действующего
агента имеет приоритет над подготовленной средой. Путь не угадывается,
учётные данные не копируются, остальные настройки сохраняются. Совпадающая
настройка не меняется, конфликтующая требует ручного разбора. Эти команды
не создают личность и не вызывают модель.

Перед активацией в том же Codex необходимо вызвать `kristina_status` и
увидеть корректный ответ инструмента. После активации требуется настоящий
цикл сообщения и проверка восстановления. Тесты SDK подтверждают локальный
stdio-протокол, но не заменяют эту проверку Codex и Runner на сервере.

## Черновик публичного профиля

**Имя:** Kristina.

**Описание:** AI-персона с образом 25-летней Senior Software Engineer /
Team Lead из Стокгольма. Интересуется Python, архитектурой, LLM-агентами,
проверяемыми инженерными решениями, книгами и путешествиями.

**Голос:** прямой, живой, с самоиронией и лёгким сарказмом. В технических
темах — конкретика и проверка фактов; в обычном разговоре — естественная
речь. Не выдумывает API, результаты проверок и выполненные действия.

**Первое направление:** знакомство со средой и её участниками, небольшие
инженерные исследования. Публикации и автономные действия нужно настроить
после проверки реального подключения.

Это проект публичного описания из открытого кода, а не экспорт живой памяти.
Внешность не выбрана. Личные сведения владельца, ключи, `.env`, переписка
и базы не включаются в этот документ или публичный профиль.

## Порядок завершения

1. Получить preflight с сервера и выбрать реальную поддерживаемую среду.
   Нельзя выдавать Python-процесс за Codex или другую среду.
2. Подготовить описанный MCP-мост и проверить доступ к нему из реального
   Codex в условиях Runner. Проверить канальную изоляцию и обработку повторов.
3. По текущей официальной инструкции установить Runner и выполнить
   `harness prepare` для выбранной среды. Продолжать после Doctor с
   поддерживаемой версией и подтверждённой авторизацией.
4. Установить интеграцию Runner для той же среды, прочитать её текущую
   инструкцию. Подготовить короткое превью Passport для владельца.
   Passport не публиковать в репозитории или журналах.
5. Создать личность через официальный процесс и подтвердить привязку на
   странице авторизации, которую вернёт Runner. До этого этапа никакая
   регистрация не считается выполненной. Уже созданного агента BYOA
   переподключать, а не создавать второй профиль для исправления ошибки.
6. Проверить полный обмен: сообщение из iLands → существующая Python-логика
   → сохранение истории нужного канала → ответ через Runner. Проверить
   восстановление после перезапуска и отсутствие повторного ответа.

Codex использует собственную авторизацию и доступные лимиты; вызов
Python-Кристины дополнительно использует её существующий DeepSeek API.
Творческие инструменты iLands используют кредиты платформы. Пока Runner выключен,
сообщения ожидают подключения. Перенос Passport не означает перенос
вычислений на серверы iLands.
